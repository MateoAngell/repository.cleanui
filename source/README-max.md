# Max source recovery and unpublished candidates

`slyguy.max.cleanui/` was recovered byte-for-byte from the published
`slyguy.max.cleanui/slyguy.max.cleanui-0.3.2.zip` in commit
`24d5f680ea2a1383681fe05e822f58348654b3d5`. It starts as 66 files, with ZIP SHA-256
`6f636e7504d183fed3341e9c38888082ed465488860d09025c287d28f5f537b8`.
The original ZIP, its SHA, published mirror manifest, repository index and
Disney packages remain untouched. This source is not the installed OpenCode
variant or the abandoned shortcut experiments.

## Edit boundary

Presentation work belongs under `resources/lib/ui/` and `resources/skins/`.
Everything else stays byte-identical, except `addon.xml` version and metadata
news. The full intro MP4 and its video XML, UI entry, intro, playback, session
and private diagnostics modules are additionally protected as complete files.

`slyguy.max.cleanui.protected.json` records 21 whole-file hashes, all baseline
file hashes and 22 protected `UIController` method fingerprints. Those methods
own playback, stop, window/session close, pending playback and restoration.
Presentation methods such as `_present_detail` can change; `_run_player`,
`play`, `_show_window`, `_close_all_windows` and the other recorded methods
cannot change their AST. Comments and formatting are allowed. Python 3.8 Index
wrappers and newer empty type-parameter fields are normalized for portability.

The constructor re-derives this policy from the pinned published ZIP. Editing
the JSON cannot silently approve a changed backend. A genuine future backend
or baseline change requires a separately reviewed policy/tool change.
`source/.gitattributes` disables line-ending conversion only for recovered Max
files, so a Windows checkout does not alter protected bytes.

These guards establish integrity, not a sandbox or proof that presentation
code has no indirect behavioral effect. Source review and runtime testing are
still required. They do not freeze the separately installed SlyGuy dependency.

## Local commands

From the repository root:

```text
python -B tools/build_max_candidate.py --verify-only
python -B -m unittest discover -s tests -p test_max_release.py -v
python -B tools/build_max_candidate.py --version 0.4.0
```

The builder never imports addon/Kodi code. It checks protected bytes and ASTs,
Python 3.8 syntax, XML/SVG, paths, symlinks and case collisions. It creates a
ZIP, SHA-256 sidecar and JSON report in the sibling `../max-candidates/` folder
by default. `--output-dir` can select another folder outside this publishing
checkout; writing candidates inside the checkout is refused.

Output names include `candidate` and a hash prefix. Existing releases are not
replaced and nothing is indexed, committed, pushed or uploaded. Source files
are never rewritten: the requested numeric version is applied only to the
packaged manifest. Version 0.4.0 is an unvalidated candidate until the complete
presentation work and acceptance runs are finished.

ZIP members are sorted, have a fixed 1980 timestamp, fixed creator/attributes
and DEFLATE level 9. Identical inputs produce identical bytes with the same
Python/zlib toolchain, independent of filesystem timestamps. The JSON records
Python/zlib versions; cross-toolchain byte identity has not been claimed.
Generated bytecode is excluded. Source changes and deleted presentation files
are listed in the report.

## Publication boundary

The integrity suite also checks the existing repository's unique IDs, exact
index MD5, active ZIP/mirror manifests, CRC and published SHA sidecars. It does
not regenerate any of them. After the single complete release is approved,
publication can copy the exact accepted ZIP to the canonical numeric filename,
record its SHA and prepare the index using the usual repository workflow.
That promotion is intentionally a separate action, absent from this builder.

The historic 206 Max UI tests were reported in release notes but their complete
suite is not present in this publishing checkout or the 0.3.2 ZIP. The new
integrity/publication tests are not a replacement for them and do not claim
visual fidelity, successful authentication, playback, audio or performance.
Keep the exact candidate hash with the local runtime observations before the
final publication; local emulator results do not establish physical theater
audio output.
